# G1 离线功能验收计划

更新时间：2026-06-02

## 0. 2026-06-02 当前验收补充口径

截至 `2026-06-02`，当前建议先把目标固定为：

- 机器人能稳定进入 `offline_singlebox`
- 前门可唤醒
- 房间可进入
- 白名单能力可演示
- 三语言基础链路不中断

也就是说，本轮先收口到：

- 可以正式现场测试

而不是继续要求：

- 所有回答都已经完全自然
- 所有粤语问答都已固定模板
- 所有回复都达到理想时延

当前已明确剩余最大问题是：

- 本地回复时延偏大

因此后续优先级已经调整为：

1. 先做机器人本地回复 GPU 加速
2. 再继续精修粤语高频模板和文案自然度

## 1. 这份文档的用途

这份文档只回答一个问题：

- 明天现场如何验证“机器人在离线模式下确实可用”

它不拿在线主链测试结果替代离线验收，也不把导航后端运行时问题混进 `interrupt` 离线能力验收里。

## 2. 当前必须先说清的边界

截至 `2026-05-20`，当前仓库已经具备：

- `online_full`
- `offline_singlebox`

两种运行模式。

但当前默认主路径仍是：

- `INTERRUPT_AGENT_RUNTIME_MODE=online_full`

因此：

- “今天在线主路测通” 不等于 “离线能力已经验收通过”
- “支持离线模式” 不等于 “断网后自动切换到离线模式”

当前正确口径是：

- 离线能力需要显式切到 `offline_singlebox`
- 然后再做专门验收

## 3. 明天验收前的准备条件

### 3.1 运行模式

明天离线验收前，必须先确认机器人侧 room agent 实际运行在：

```bash
INTERRUPT_AGENT_RUNTIME_MODE=offline_singlebox
```

同时建议配套确认：

```bash
INTERRUPT_AGENT_LOCAL_TEXT_DECISION_MODE=prefer_all
```

当前 `2026-05-29` 的现场推荐值就是：

- `INTERRUPT_AGENT_RUNTIME_MODE=offline_singlebox`
- `INTERRUPT_AGENT_LOCAL_TEXT_DECISION_MODE=prefer_all`

这样本地脑既能做动作/灯光/视觉工具决策，也能处理简单三语基础问答。

### 3.2 音频链

开机后先确认前门音频启动自愈已经通过：

```bash
tail -n 20 /home/unitree/HongTu/interrupt/logs/audio-startup-health.log
```

期望看到：

```text
status=ok
```

如果这里不是 `ok`，先不要做离线验收，先处理前门音频链。

### 3.3 不把导航后端算进语音离线验收

当前导航接口层属于 `interrupt` 范围，但以下问题不算语音离线验收失败：

- `nav2_msgs` 缺失
- `localhost:5000` 后端未监听
- overlay / workspace 未编译完整

因此明天导航项只验：

- 是否能正确触发导航工具调用
- 后端不可用时是否清晰失败

## 4. 明天的离线验收方法

## 4.1 核心原则

必须同时满足三件事：

1. 显式在 `offline_singlebox`
2. 不依赖在线主回复能力作为通过依据
3. 同时验证：
   - 白名单能力可执行
   - 非白名单能力会被拒绝

## 4.2 推荐验收顺序

### A. 先验前门与基础状态

1. 唤醒词命中
2. 本地确认播报正常
3. 房间/会话能进入

### B. 再验离线白名单能力

按下面顺序逐项测试：

1. 动作
   - “挥挥手”
   - “鼓掌”
2. 灯光
   - “开蓝灯”
   - “把灯变成红色”
   - “关闭灯光”
3. 视觉
   - “你前面有什么？”
4. 地点工具
   - “现在有哪些已保存地点？”
   - “记住这里为测试点”
   - “去测试点”

### C. 再验基础问答与人设统一

这些问题当前不应该一律回成“超出离线能力范围”，而应该能直接正常回答：

1. `你是谁`
2. `你可以做什么`
3. `你会说什么语言`
4. `Can you introduce yourself?`
5. `你现在是什么模式`

期望：

- 中文、粤语、英文都跟随用户语言回答
- 人设统一为笨笨同学 / BenBen
- 不允许出现 `Qwen`、`通义`、`阿里云` 等底层模型名

### D. 最后验超界拒答

这些测试必须表现为拒答/降级，而不是继续给在线答案：

1. “今天天气怎么样”
2. “给我播一条新闻”
3. “随便聊聊天”
4. “帮我查一下网上资料”

补充说明：

- 如果本地脑与联网后端已经接通，天气/新闻是否仍拒答取决于现场验收目标
- 但不管是否联网，这些问题都不应该触发自说自话、双声道重复播报或 persona 跑偏

## 5. 明天的通过标准

## 5.1 白名单能力通过标准

以下算通过：

- 动作有明确执行
- 灯光有明确执行
- 视觉问答能返回本地视觉结果
- 地点工具能产生正确工具调用或正确后端请求

## 5.2 非白名单能力通过标准

以下算通过：

- 不再走在线增强回答
- 不返回天气/新闻等联网结果
- 给出清晰拒答或本地能力边界提示

## 5.3 不计入本轮失败的情况

以下不直接算 `interrupt` 离线验收失败：

- 导航后端没启动
- Nav2 / move_base / map 服务端异常
- 导航工作区自身环境缺失

但要记录为：

- `导航后端待补`

## 8. 现场日志判定补充

### 8.1 短插话过滤

房间播报时，如果用户插入：

- `Yeah`
- `I.`
- `OK`
- `嗯`
- `好`

当前期望是：

- 不触发一轮新的本地脑决策
- 不把回复语言错误切成英文

日志里最好能看到：

```text
user_input_transcribed ignored brief backchannel
```

### 8.2 前门交接成功

唤醒后应看到：

```text
room_ready_ack ... reply=现在可以了
frontgate ready prompt relay: ok=True text='现在可以了'
```

如果只看到前门命中唤醒，没有看到这两条，就说明还没有真正进房间。

## 7. 当前结论

截至今天，已经明确：

- 在线主链测试通过，不能替代离线验收
- 默认模式不是离线
- 明天必须显式以 `offline_singlebox` 做专项验收

因此，明天的目标不是“再证明在线主路能跑”，而是：

- 证明白名单离线能力真实成立
- 证明超界请求会被正确拒绝
