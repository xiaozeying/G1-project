### 当前代码层关键口径

- 空闲待唤醒：蓝灯
- 会话监听中：绿呼吸灯
- 动作执行中：紫灯
- 用户 `away` 超时：`300000ms`
- 真机默认 G1 接口：`eth1`
- 真机会话默认 PortAudio 设备：`input=0` `output=0`

### 当前已知问题与对应结论

1. “收到指令但没执行”

- 根因不是 ASR 没收到
- 真机日志已经确认存在 `server cancelled tool calls`
- 这会导致 Gemini 端准备调用工具，但在真正执行前被取消
- 当前已增加本地控制快路，明确灯光/动作命令优先本地落地，减少这类失败

2. “动作执行后第二轮语音容易丢”

- 根因是 `console` 输入流有概率静默停摆
- 当前已在 [src/console_audio_compat.py](/home/zz/HongTu/interrupt/src/console_audio_compat.py) 加输入 watchdog
- 当回调停摆时会自动重开输入流

3. “灯态和真实状态不一致”

- 已移除 `session.start()` 返回后立即回蓝灯的误逻辑
- 当前蓝灯只应由真正 `away -> shutdown` 驱动

4. “天气/新闻不能实时查”

- 当前不是网络临时抖动，而是架构上没有接入外部实时数据工具
- [config.yaml](/home/zz/HongTu/interrupt/config.yaml) 里的 `integrations.mcp_stdio_command` 与 `mcp_http_urls` 当前均为空
- 所以机器人会话里没有 weather/news 实时工具，模型只能给非实时兜底回答

### 下一次继续推进时的优先顺序

1. 继续验证“本地控制快路”是否彻底压住 `server cancelled tool calls`
2. 继续观察动作后输入 watchdog 是否能把第二轮指令接稳
3. 单独接入 weather/news 外部工具链，不与灯光/动作链路混改
4. 最后再做文案、体验类优化

## 项目最终目标

本项目最终不是只做一个本地 demo，而是要形成一套可演进的语音对话系统底座，满足下面四个方向：

1. 本地可运行的、支持打断的实时语音对话系统。
2. 架构上对齐 LiveKit Agents / LiveKit Playground 的能力模型。
3. 后续接入外部三语言唤醒词模块。
4. 后续接入 MCP 工具链，并逐步扩展为可落地的智能体系统。

最终目标形态：

```text
唤醒词模块
  -> 本地语音会话入口
  -> LiveKit Agents runtime
  -> Gemini Live realtime model
  -> MCP tools
  -> 后续业务能力 / 终端设备 / G1 等外部系统
```

## 今天定位出的关键问题

### 1. 之前“不支持打断”的核心原因

之前日志显示：

- agent 在说话
- 用户最终转写能出来
- 但在 agent 播报期间，没有捕捉到真正的“用户说话中断事件”

也就是：

```text
不是“检测到打断但没停”
而是“根本没有在 agent 说话期间把用户开口识别成 interruption”
```

因此今天的调整重点从“改回复逻辑”切到了“先让 interruption detection 真正触发”。

### 2. 双声音 / 像两个 AI 在说话

这个问题大概率与重复启动或重复会话有关，而不是模型本身会自言自语。

今天看到的证据：

- 日志里曾有多次 console/job 初始化记录
- 之前用户也反馈过像有两路声音

这件事明天需要继续收口，目标是保证任何时刻只有一条本地主会话。

## 明天建议的实现步骤

建议按下面顺序推进，不要再同时追网页端、MCP、唤醒词三条线。

### 阶段 1：彻底收口本地可打断语音链路

目标：

- 本地语音链路稳定运行
- 普通插话可打断
- 停播类插话可返回固定话术
- 不再出现双声音

具体步骤：

1. 只保留一个本地 agent 进程运行。
2. 用耳机测试，不用外放。
3. 连续做三组验证：
   - 普通插话
   - “等一下 / 停一下 / 先别说了”
   - 长回答中途打断
4. 如果仍有不稳定，继续看 [logs/agent.log](/home/zz/HongTu/interrupt/logs/agent.log) 里的：
   - `user_state_changed`
   - `agent_state_changed`
   - `user_input_transcribed`
   - `overlapping_speech`
5. 必要时把“打断确认话术”从提示词级逻辑改成程序级逻辑。

完成标准：

- 本地语音链路可稳定复现打断。

### 阶段 2：把“固定确认话术”做成程序级逻辑

目标：

- 用户说“停一下 / 等一下 / 先别说了”时，不依赖模型临场发挥
- 由代码层保证停播后回一句固定确认话术

建议方向：

1. 继续利用转写事件。
2. 当满足以下条件时，触发固定逻辑：
   - agent 当前处于 `speaking`
   - 用户转写命中停播类短语
3. 代码主动结束当前语音句柄并播报固定句。

完成标准：

- 固定确认话术可预测、可复现、不靠模型猜。

### 阶段 3：引入外部三语言唤醒词模块

目标：

- 当前“常开麦模式”改成“唤醒后进入会话”

建议做法：

1. 先不要把外部唤醒词代码直接塞进 `interrupt` 主逻辑。
2. 先定义一个适配接口。
3. 外部模块只负责：
   - 监听音频
   - 检测唤醒词
   - 触发会话开始
4. `interrupt` 负责：
   - 会话管理
   - 打断
   - MCP
   - 回复逻辑

完成标准：

- 唤醒词与会话系统解耦，可插拔。

### 阶段 4：接入 MCP

目标：

- 让本地语音智能体具备可调用工具能力

建议顺序：

1. 先用最简单的本地 stdio MCP 做通路验证。
2. 先接 1 个最简单、最容易观察结果的工具。
3. 等 MCP 通路稳定后，再扩展复杂工具集。

完成标准：

- agent 可通过语音触发 MCP 工具并返回结果。

### 阶段 5：是否回到网页端

只有在本地主路径完全稳定后，才决定是否继续做网页端。

判断标准：

- 如果需求只是“本地支持打断的语音系统”，则网页端不是当前必需。
- 如果未来一定要做 LiveKit Playground 同款前端体验，再回头处理网页端调度和房间问题。
